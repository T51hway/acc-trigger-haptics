## 一、这个项目是什么

给 **Assetto Corsa Competizione（ACC）** 做一个外部程序：读游戏遥测，驱动 Xbox 手柄的**四个马达**——
两个握把 + 两个扳机。ACC 原生只震握把，扳机是空的。

核心目标是**让扳机告诉你轮胎到没到极限**（刹车抱死、出弯打滑）。
扳机马达更适合干这个：它贴指尖，反应快，而且不占握把的带宽。

完整设计在 `设计说明.md`，那份文件是决策记录，**改之前必须先跟用户确认**。

## 三、三条最重要的实测结论

### 1. 扳机只能走蓝牙 HID 报文

三条路都试过，只有 HID 真的能驱动：

| 通道 | 结果 |
| --- | --- |
| **蓝牙 HID 输出报文 0x03** | ✅ 可用，四马达全控，**不受前台焦点限制** |
| Windows.Gaming.Input | 能枚举、能写入、读回值也对，**但马达不响** |
| GameInput | 这台机器上**读不到任何设备**（连键盘鼠标都读不到） |
| XInput | 只能两个握把 |

报文格式（9 字节，值 0~100）：
`03 0F <左扳机> <右扳机> <左握把> <右握把> FF 00 EB`

### 2. 判断 HID 能不能发振动，必须"试写"，不能查能力

`HidP_GetCaps` 返回的 `OutputReportByteLength` 是 **0**，但直接 `WriteFile` 9 字节报文**能写进去、马达会震**。

原因：它只报**第一个顶层集合**（手柄输入）的能力，而震动报文在同一个设备的**另一个集合**里。

**正确做法**：打开设备后发一个全零报文，能写进去就算这条通道可用。
（参考项目 `asasiton/lmu-` 里那句 `OutputReportByteLength == 9` 的筛选也是猜的，会把可用设备筛掉。）

### 3. ACC 每帧重写四个马达，必须屏蔽它的写入

ACC 每帧调 `XInputSetState`，**一次重写四个马达，把两个扳机清零**。我们刚写的扳机震动被它下一帧冲掉 → 表现为"断续、强度不足"。

**把游戏内震动调到关闭也没用**——实测它仍然每帧发零值（关闭只影响"震多少"，不影响"发不发"）。

解法：`AC2\Binaries\Win64\` 放一个自编译的 `xinput1_3.dll`（`tools/xinput_proxy/`）：
读手柄的调用全部转发给系统那份，**只吃掉 `XInputSetState`**。

**效果**：赛道上扳机又稳又满，而且 **60Hz 就够**（120/200Hz 没有更好）。
→ 写入频率与遥测 333Hz 彻底脱钩。

## 四、ACC 字段的实测量纲（写代码直接用）

| 字段 | 实测结论 |
| --- | --- |
| `slipRatio[4]` | **float**（文档标 int 是错的）。无量纲，前轮 -1.0 = 完全抱死 |
| `wheelSlip[4]` | **弃用**。数值到 222，与"滑移比×车速"对不齐，含义不明 |
| `accG[3]` | **车身坐标，但轴序是 X=横向、Y=垂直、Z=纵向** |
| `kerbVibration` | ±0.1 截断，×10 才是 0~1 |
| `slipVibrations` | ±1 截断，62% 的帧都 >0.02 |
| `gVibrations` | 0~7.5，不截断，91.5% 的帧都 >0.02 |
| `absVibrations` | 只剩 ±1/0 的方波 = "ABS 正在动作" |
| `brakePressure[4]` | 不是 bar，是"刹车输入 × 前后分配比"：同轴左右相同，前+后=1。这次实测前 0.742 / 后 0.258（换车/改刹车平衡会变） |
| `gear` | 原始值从 0 起算：**0=R、1=N、2=1 档**、3=2 档……**换挡瞬间会短暂报 1（约 75ms）**。代码里 `gear_raw` 保留原值，`gear` 已减 1，`gear_label` 直接显示 R/N/数字 |
| `wheelLoad[4]` | **行驶中也全是 0。** 2026-11-25 实测 4412 帧、最高 252 km/h，一个非零都没有。这个字段在 ACC 里基本没用（原本的路肩分边已删除，引擎现在不读它） |
| `slipAngle[4]` | **弧度**。同一份实测：正常过弯 p90 约 0.14、推头段 0.19~0.21、打转/出界能到 1.5（≈87°）。推头判据用"前轮 − 后轮"的差值，不用绝对值 |

`accG` 轴序的证据：corr(accGx, 车速×横摆角速度/9.81) = **-0.927**；
直线重刹时 accGz 平均 **-1.61**，全油门加速时 accGz 中位 **+0.47**。
**按字面理解会把刹车读成横向。**

## 七、已经踩过的坑（别重犯）

1. **`HidP_GetCaps` 假阴性** —— 见第三节第 2 条。判断能力要试写。
2. **WGI 的设备列表是延迟填充的** —— 第一次查 0 个，等 1 秒就有。
   **任何探测都必须轮询重试**，查一次就下结论会得出完全错误的判断（我因为这个错了两次）。
3. **代理 DLL 的导出表序号** —— 系统那份 `xinput1_3.dll` 第 1 号是 `DllMain`，
   真正的函数从第 2 号开始。用 `.def` 必须显式写序号并逐个对齐，
   否则按序号取函数会拿到错的函数 → ACC 直接 UE4 fatal error。
   正确序号：`GetState@2`、`SetState@3`、`GetCapabilities@4`、`Enable@5`、
   `GetDSound@6`、`GetBattery@7`、`GetKeystroke@8`。
4. **官方 ACC 文档有三处错**：`slipRatio` 类型、四个震动通道类型、`accG` 语义。别照文档写。
5. **造测试数据时别用 `Local\acpmf_physics` 这个名字** —— `CreateFileMapping` 会复用
   ACC 正在用的那块映射，等于往游戏的数据里写真值（虽然被 333Hz 覆盖了，但很危险）。
6. **用 Python 生成 .bat 时，源码里的 `\\` 会被转义成 `//`**。
   用 `os.sep.join()` 拼路径可避免；或者直接用写文件的工具写，别过 shell 的 heredoc。
7. **Bash 里调 PowerShell 会被安全策略拦**，要用专门的 PowerShell 工具。
8. **`手感设置.toml` 里注释的数字不是值。** 第一次用户把注释里的"1.0 是基准"
   改成了 4.0，真正的 `grip_kerb = 1.35` 没动，所以怎么调都没反应。
   现在文件改成行内注释（`grip_road = 0.21  # 路面纹理`），程序启动和热更新时
   都会打印**实际生效的四个数**。
9. **cmd 的码页是 936，UTF-8（无 BOM）的 .bat 里写中文文件名会失配。**
   实测：这种 bat 里 `if exist "手感设置.toml"` 判成"不存在"，
   `notepad "手感设置.toml"` 会按乱码名去找文件（表现为"找不到"或新建一个乱码名文件）。
   **修法**：`@echo off` 后面加一行 `chcp 65001 >nul`（已在 `调手感.bat` / `启动震动.bat`
   上验证有效），或把 bat 存成 UTF-8 带 BOM。
   反过来也要注意：**`.bat` 必须用 CRLF 换行**，编辑工具改完可能整份变成 LF，要复原。

### 3. `haptics_engine.py`（已完成）

- 输入：遥测快照；输出：四个马达值
- 分层：底层压力反馈（≤20%）+ 上层临界事件（≤70%）
- 混音用加权求和 + 单次软限幅，遵守"1 主 + 1 辅"预算（见 D11）
- **注意**：前轮抱死是一帧到位的，没有渐变过程，"逼近时逐渐增强"做不出来，
  只能报"已经锁死"或做"ABS 正在救你"的嗒嗒（见第五节和 D5 的修正注记）

写的时候落下的几个细节（代码里有注释，这里记一笔）：

- **ABS 的节奏由我们自己出**：每 120ms 起一个 70ms 脉冲（按起点间隔算，
  不是"脉冲结束后再等 120ms"，所以约 8.3Hz），`abs` / `absVibrations`
  只用来判断"ABS 在动作"。
  实测 `abs` 只有 0/1，而游戏方波的频率没保证；太快时 ERM 会把它抹成连续震动，
  听不出"嗒嗒"。如果听起来仍像连续震，把 `EVENT_REFRACTORY` 从 0.12 调到 0.16 试试。
- **后轮打滑用 0.6 次方，不是 D8 的 4 次方。** 0.15 的硬阈值已经负责"平时安静"，
  阈值以上再压 4 次方会让刚打滑时几乎没有反馈。D8 的 4 次方留给没有硬阈值的连续量。
- **握把的路面纹理有死区。** `gVibrations` 91.5% 的帧 >0.02，不设死区就是永远在震。
- **路肩通道已移除（2026-11-25）。** 原来按轮荷/悬挂差给左右分权重、做 300ms 峰值保持，
  用户实测后确认不需要（路面纹理本身已经覆盖了大部分路肩的粗糙感）。
  相关常量、`_load_bias()`、状态行里的"路肩峰 / 偏"都一起删了；要找回看 git 历史。
- **点窗口 × / 注销 / 关机时**，`atexit` 不会跑；`pad_driver` 用 `SetConsoleCtrlHandler`
  抢一包零，点 × 关窗口也能清。

- **D5 的 20% 底线没有改**，只是做成了可调。用户自己那份现在是
  **0.21 / 0.28 / 0.15 / 1.00 / 1.00**（顺序同上表）。
- **强度不是越大越好。** 以前把路肩拉到 4.0、路面 2.5 时，两个握把长期顶在 100%，
  路肩和左右差都被饱和抹平；现在路面基准降到 0.21，超过 0.6 一样会顶满。
- **只改等号 `=` 右边的数字**，`#` 后面是说明。第一次用户把注释里的
  "1.0 是基准" 改成了 4.0，真正的数值没动，所以怎么调都没反应。
  现在文件用行内注释，主程序启动和每次热更新都会打印**实际生效的四个数**。
- 状态行：`握把峰 L/R` 是左右握把最近 1 秒的输出峰值，`扳机` 是左右扳机的当前输出。
- 其余阈值、曲线、混音预算还在 `haptics_engine.py` 开头，等闭眼测试有结论再外放。

### 控制面板（2026-11-25 新增，未实车验证）

双击 `启动面板.bat`（本机专用）打开一个窗口：

- **四盏状态灯**：代理 DLL / 手柄 / ACC 遥测 / 震动
- **四个滑块**：拖动即写 `手感设置.toml`（保留行内注释、先写临时文件再替换），1 秒内生效
- **开始震动 / 停止震动**
- **安装接管 / 恢复原生**：ACC 正在运行时会提示先退出（运行中的 DLL 被系统锁着）

实现上的两个决定：

- **面板自带一份 60Hz 循环，不复用 `main.py`。** `main.py` 是目前唯一实车验证过的链路，
  也是出问题时的退路，故意不动；代价是循环逻辑有两份，**改判定/清零逻辑时要两边一起改**。
- **用的是 uv 装的完整 Python 3.13.3**（带 tkinter 和 pythonw），不是 PATH 里那个 0 字节
  占位符，也不是 WorkBuddy 那个缺 tkinter 的精简版。路径写死在 `启动面板.bat` 里，
  找不到时会自动退回 3.12.15。

注意：

- `pythonw` 启动没有控制台，出错只看 `panel.log`（仓库根目录，已被 gitignore）。
- 关窗口会先停止震动再退出；用任务管理器强杀则可能留下马达在震，**正常用法是点 ×**。
- 自检：用带 tkinter 的 Python 跑 `src/panel.py --selftest`，1.5 秒后自动关闭，退出码 0 即正常。

### 打包 exe（2026-11-25）

- 构建环境：`.venv-build`（用 uv 的 3.13.3 建 venv，再 `pip install pyinstaller`），已 gitignore。
- 构建命令（README 里也有）：

  ```
  .venv-build\Scripts\python.exe -m PyInstaller --noconfirm --clean --onefile --windowed ^
      --name ACC-Panel --paths src ^
      --add-data "tools\xinput_proxy\xinput1_3.dll;tools\xinput_proxy" src\panel.py
  ```

- 产物 `dist\ACC-Panel.exe` 复制到仓库根目录、改名 `ACC震动面板.exe`（已 gitignore，不进仓库）。
- **路径陷阱**：PyInstaller onefile 下 `__file__` 指向临时解压目录。
  所以 `haptics_engine.application_dir()` 和 `panel._app_dir()` 用 `sys.frozen` 判断，
  资源文件（代理 DLL）用 `sys._MEIPASS`。**exe 必须和 `手感设置.toml` 放同一层。**
- 实测：单文件约 10MB，双击到出窗口约 1.2 秒。

## 十、跟用户协作的方式

- **不懂编程**，一切用"双击 bat"，不要让他敲命令
- 中文回答，**不要用大色块图表**，喜欢朴素排版
- 有多个方案时**列清楚代价**，让他选，不要替他决定
- **改 `设计说明.md` 里的决策前必须先确认**
- 他经常能给出正确的直觉（比如"关掉 ACC 震动""删掉不用的 bat"），
  但有时结论需要实测校验（比如"关掉 ACC 震动"实测不够）
- 他的机器上踩过的坑比文档里写的多，遇到怪现象先怀疑环境和驱动
